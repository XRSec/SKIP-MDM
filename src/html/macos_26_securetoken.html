为什么人工建号与 macOS 26 切换账户不再自动授权？

        

          人工通过 dscl、脚本或 MDM PreStage 创建的管理员若未封装 Secure Enclave 密钥，仅具备传统 POSIX sudo 权限。在 macOS 14–26 的架构演进下，早期所有偏门补救路径均已封堵。
        

      


      
      

        
1. SecureToken 与 Volume Owner 的底层密码学绑定

        

          

            

              在采用 APFS 的现代 Mac（搭载 T2 安全芯片或 Apple Silicon）上，Apple 官方部署指南将 SecureToken（安全令牌） 定义为由用户登录密码保护并封装的 密钥加密密钥（KEK, Key Encryption Key）。
            

            

              在 Apple Silicon 架构下，SecureToken 与 Volume Ownership（卷宗所有权） 硬件级绑定在安全隔区（Secure Enclave）内：系统上第一个获得 SecureToken 的用户自动成为首个卷宗所有者（Volume Owner）。
            

            

              关键边界：没有 SecureToken 的管理员仅具备传统 POSIX 意义上的 sudo 权限，在 macOS 安全子系统中属于“名义管理员”，不具备任何密码学授权能力。

2. 人工或脚本创建用户导致 SecureToken 缺失的三大原因

        

          

            
01 · 跳过设置助理

            
未触发 OpenDirectory 验证钩子

            

              跳过开机设置助理后，通过命令行新建的账户在完成首次交互式图形登录或 dscl . -authonly 密码校验前，不会生成令牌。
            

          

          

            
02 · 存在禁用标记

            
写入了 SecureToken 禁用标签

            

              Jamf 二进制账户、aws/ec2-macos-init 等工具常在 AuthenticationAuthority 追加 ;DisabledTags;SecureToken；标签存在期间改密或登录均不会签发令牌。
            

          

          

            
03 · UID 阈值抑制

            
UID 小于 500 不会获发令牌

            

              据 freegeek-pdx/mkuser 文档，当用户 UID 被设为 500 以下（常用于隐藏管理账户）时，macOS 在验证其密码时默认不授予首个 SecureToken。

解救陷入 Activate Mac 死锁的三种方案（由轻到重）


        

          

            

              方案一 · 保留数据首选
              不抹除内部 SSD
            

            
突破 Activate Mac 网络与 iCloud 条款拦截

            
    
              
  1. 改用手机个人热点或 USB-C 有线网卡：即使右上角显示 Wi-Fi 已连接，底层激活请求仍常因路由器/DNS/ISP 握手失败；改连 iPhone USB 共享热点或有线网卡并重启后常可通过。
    2. 
              
  2. 在另一台设备提前接受新版 iCloud 条款：若曾绑定 Apple ID，用手机或他机浏览器登录 icloud.com 同意所有新条款后再重启故障机，避免条款框渲染卡死。
    3. 
              
  3. 全量重置全部本地用户密码：遵循 Addigy 规范，激活后进入 resetpassword 时务必为每一个本地账户重设密码（漏改任一账户会导致重启失效并再次锁死）。
    4. 
            

          


          

            

              方案二 · 单机抹除（清数据）
              无需第二台 Mac
            

            
通过屏幕左上角菜单栏调用“抹掉 Mac”

            
    
              
  1. 无需进常规四宫格恢复模式，直接在卡住的 Activate Mac 或 Activation Failed 界面，将指针移到屏幕最左上角菜单栏。
    2. 
              
  2. 点击 恢复助理 (Recovery Assistant) > 抹掉 Mac... (Erase Mac...) 并确认抹除。
    3. 
              
  3. 此操作会清除损坏的 APFS 宗卷组与无令牌残留；自动重启后连接 Wi-Fi 或手机热点等待数分钟完成激活，随后点击 退出到恢复实用工具 (Exit to Recovery Utilities) 重装 macOS。
    4. 
            

          

        


        
        

          

            

              方案三 · 双机 Apple Configurator 2 硬件级 DFU
              需宿主 Mac + 数据 USB-C 线
            

            

              若左上角菜单无响应或换热点仍报 Failed to Activate Device，请准备另一台运行 macOS 15.7+ Sequoia（Apple Configurator v2.19） 或 macOS 26.x Tahoe 的宿主 Mac，用支持数据传输的 USB-C 线连接故障机 DFU 端口进入 DFU 模式。
            

            

              

                
DFU Revive（唤醒）

                
保留用户数据：仅重刷安全隔区固件、iBoot 与 RecoveryOS。实测多数情况无法解除此激活报错，仅在有未备份关键数据时作抢救尝试。

              

              

                
DFU Restore（恢复 · 终极解法）

                
彻底抹除全部 APFS 容器并重刷 IPSW：将机器重置为出厂开箱状态，重启后不再出现 Activate this Mac 拦截界面。

              

            

          


          

            

              
四种死锁救援手段：成功率 vs 数据保留

              

            

            

              决策速查：保数据 → USB 热点 + icloud.com 同意条款 + 全量改密；不保数据 → 菜单栏抹掉 Mac 或双机 DFU Restore。

          关键避坑 · 为什么模式 D（Self-Grant 自我赋权）在 macOS 26 失效？
          Fabien Conus 于 2026 年 8 月 31 日确认：macOS 11–15 常用的“无令牌时把同一个管理员同时传入 -adminUser 和 -secureTokenOn”的技巧在 macOS 26 Tahoe 已失效。系统提前生成 Bootstrap Token 并准备了 FileVault 上下文，强行自签会直接报错：Operation is not permitted without secure token unlock。
